1 · Présentation du projet

Portfolio professionnel présentant le parcours, les compétences et les réalisations de Guillaume Hurard. L'ensemble du contenu est administrable : rien n'est écrit en dur dans les templates, tout provient de la base et se modifie depuis une interface d'administration protégée.

Fonctionnalités principales

  • Page d'accueil unique découpée en sections : à propos, compétences, expériences, formations, projets, certifications, contact.
  • Pages projet détaillées avec galerie d'images, vidéo de couverture, contexte, objectifs, fonctionnalités et documentation téléchargeable.
  • Bilinguisme français / anglais avec des URL distinctes et traduites.
  • Formulaire de contact avec anti-spam, enregistrement en base, notification par e-mail et accusé de réception au visiteur.
  • Back-office EasyAdmin couvrant les 9 entités de contenu, avec réordonnancement, publication à la carte et upload de médias.
  • Export / import JSON de l'intégralité du contenu, pour sauvegarde ou transfert entre environnements.
  • Thème clair / sombre mémorisé côté navigateur.

Public & contexte

Le site s'adresse à des recruteurs, clients potentiels et pairs développeurs. Il fait aussi office de démonstration technique : l'architecture, la sécurisation et la chaîne de déploiement sont volontairement traitées comme celles d'une application de production, et non comme une simple page vitrine.

Choix structurant : le contenu est administrable plutôt qu'écrit en dur. Cela permet de mettre à jour un parcours, ajouter un projet ou publier une certification sans toucher au code ni redéployer.

4 · Authentification & sécurité

Connexion & contrôle d'accès

Un seul pare-feu applicatif (main) couvre le site, avec un fournisseur d'utilisateurs Doctrine indexé sur l'e-mail. Les mots de passe utilisent l'algorithme auto de Symfony, qui sélectionne le meilleur disponible. L'accès à l'administration est verrouillé par une règle unique : ^/admin exige ROLE_ADMIN.

# config/packages/security.yaml
firewalls:
    main:
        form_login:
            enable_csrf: true
        # Sans cela, /login accepte un nombre illimité de tentatives.
        login_throttling:
            max_attempts: 5
            interval: '15 minutes'

access_control:
    - { path: ^/admin, roles: ROLE_ADMIN }

Transport & en-têtes

Le trafic est intégralement chiffré : public/.htaccess redirige le port 80 vers HTTPS en 301 et émet un en-tête HSTS d'un an, uniquement sur les réponses déjà chiffrées. Les hôtes locaux sont exclus de la redirection pour ne pas gêner le développement.

Limite assumée de la CSP : script-src doit conserver 'unsafe-inline' et data:. L'AssetMapper génère un bloc <script type="importmap"> en ligne, et fait pointer les entrées CSS vers un module data:application/javascript, vide. Sans ces autorisations, tout le JavaScript du site cesse de fonctionner silencieusement, protection CSRF côté client comprise. L'apport anti-XSS de la CSP est donc partiel ; la protection réelle contre le XSS reste l'échappement automatique de Twig, qui n'est contourné nulle part (aucun filtre |raw dans les templates). Le gain concret porte sur frame-ancestors, object-src 'none', base-uri et form-action.

Protection CSRF

Les formulaires Symfony intègrent un jeton CSRF par défaut : c'est le cas du formulaire de contact et du formulaire de connexion (enable_csrf: true). L'import de données, qui n'utilise pas le composant Form, valide son jeton manuellement.

// src/Controller/Admin/DataController.php — import destructif, triple garde
if (!$csrfTokenManager->isTokenValid(new CsrfToken('admin_data_import', $token))) { /* refus */ }
if (!$request->request->getBoolean('confirm'))                       { /* case de confirmation */ }
// + l'attribut #[IsGranted('ROLE_ADMIN')] sur la classe entière

Uploads

Les médias déposés depuis l'administration présentent deux risques : un nom de fichier contrôlé par l'utilisateur, et l'exécution du fichier déposé. Les deux sont traités.

  • Renommage systématique : setUploadedFileNamePattern('[randomhash].[extension]'), le nom d'origine n'est jamais réutilisé.
  • Contraintes de type sur les 7 champs d'upload : images limitées à JPEG, PNG, WebP et GIF (4 Mo), vidéos à MP4 et WebM, documentation au PDF. Le SVG est volontairement exclu car il peut embarquer du script et serait servi depuis notre propre domaine.
  • Exécution neutralisée : public/uploads/.htaccess supprime tout handler PHP et refuse l'accès aux extensions exécutables.
Vérifié en conditions réelles : avant ajout de ce .htaccess, un fichier PHP déposé dans public/uploads/ était réellement exécuté par le serveur. La protection a été validée par un test : le fichier renvoie désormais 404 tandis que les images légitimes continuent d'être servies. L'upload étant réservé aux administrateurs, il s'agit de défense en profondeur — la chaîne devient dangereuse seulement si un compte admin est compromis.

Exposition des fichiers & secrets

La racine web ne pointe pas sur le dépôt mais sur son seul dossier public/, via un lien symbolique (voir §8). Le code source, vendor/, les logs et les fichiers d'environnement sont donc hors d'atteinte : une requête sur /.env, /.git/config ou /composer.json renvoie 403 ou 404.

Les secrets de production (APP_SECRET, accès base, MAILER_DSN) vivent dans un .env.local présent uniquement sur le serveur, en permissions 600, jamais versionné. Le .env du dépôt ne contient que des valeurs par défaut inoffensives (MAILER_DSN=null://null).

Contrôlé sans anomalie : aucune vulnérabilité connue dans les dépendances (composer audit), aucun |raw dans les templates, requêtes exclusivement via Doctrine (pas de SQL concaténé), cookie de session en secure; httponly; samesite=lax.

6 · Formulaire de contact & e-mails

C'est le seul point d'entrée où un visiteur non authentifié écrit en base. Il combine trois protections et déclenche deux envois d'e-mail indépendants.

Anti-spam

  • Jeton CSRF — fourni par le composant Form.
  • Honeypot — un champ website invisible ; s'il est rempli, c'est un robot.
  • Anti-flood par IP — 3 messages maximum par tranche de 10 minutes, comptés via l'index composite de contact_message.

En cas de détection, le site affiche le même message de succès que pour un envoi valide, sans rien enregistrer. C'est délibéré : indiquer au robot ce qui l'a bloqué lui permettrait d'ajuster sa stratégie.

// src/Controller/HomeController.php
$isSpam = (bool) $contactForm->get('website')->getData()
    || $contactMessageRepository->countRecentFromIp($ip, 10) >= 3;

if (!$isSpam) {
    $entityManager->persist($contactMessage);
    $entityManager->flush();          // la trace en base précède les envois

    $contactNotifier->notify($contactMessage, $profile?->getContactEmail());
    $contactNotifier->acknowledge($contactMessage, $locale);
}

Deux envois strictement indépendants

Expéditeurcontact@guillaumehurard.frno.reply@guillaumehurard.fr

Les deux méthodes sont appelées séparément, chacune protégée par son propre try/catch. L'échec de l'une n'empêche jamais l'autre, et aucune ne peut faire échouer la requête : le message est déjà persisté avant le premier envoi. Les deux expéditeurs sont volontairement distincts — l'adresse de réponse réelle d'un côté, une adresse dédiée jamais relevée de l'autre.

Envoi via le sendmail local, pas en SMTP authentifié. MAILER_DSN="native://default". L'application tourne sur le même serveur que la messagerie : s'authentifier en SMTP auprès de mail.guillaumehurard.fr depuis cette même machine n'apporte rien et introduit un mot de passe à gérer. Une tentative en SMTP authentifié a d'ailleurs échoué durablement en 535 Incorrect authentication data ; le passage au sendmail local a supprimé le problème plutôt que de le résoudre.
Piège à connaître : ContactNotifier dépend de MailerInterface et est injecté dans HomeController::index(). Un MAILER_DSN invalide fait donc échouer toute la page d'accueil en erreur 500, et pas seulement la soumission du formulaire.
Mailer en mode synchrone. Le routage de SendEmailMessage vers le transport async est commenté dans messenger.yaml. Sur un hébergement mutualisé, aucun worker messenger:consume ne tourne : les messages resteraient indéfiniment en file d'attente en base. L'envoi se fait donc pendant la requête.

7 · Internationalisation

Le site est bilingue français / anglais, le français étant la langue par défaut. Deux mécanismes coexistent, selon la nature du texte.

Textes d'interface : fichiers de traduction

Les libellés de l'interface passent par le translator, avec une convention inhabituelle mais assumée : les clés de traduction sont le texte français lui-même. Il n'existe donc pas de messages.fr.yaml — en français, le mécanisme de repli affiche la clé, qui est déjà le bon texte. Seul messages.en.yaml existe (44 clés), plus validators.en.yaml pour les messages de validation.

Contenus éditoriaux : colonnes doublées

Les contenus saisis en administration ne peuvent pas vivre dans des fichiers de traduction. Chaque champ traduisible est donc doublé en base avec un suffixe En : description / descriptionEn, aboutText / aboutTextEn, etc. Les entités exposent des accesseurs localisés (getLocalizedAboutParagraphs($locale)) qui retombent sur le français si la version anglaise est vide — un contenu non traduit reste donc affiché plutôt que de laisser un trou.

URL localisées

La locale n'est pas transportée par un paramètre de requête mais inscrite dans la route elle-même, ce qui donne des URL propres et indexables séparément.

// Une seule route, deux chemins : la locale est déduite de l'URL empruntée.
#[Route(path: ['fr' => '/',             'en' => '/en'],              name: 'home')]
#[Route(path: ['fr' => '/projets/{slug}', 'en' => '/en/projects/{slug}'], name: 'project_show')]

C'est ce qui permet à l'accusé de réception du formulaire de contact d'être rédigé dans la bonne langue sans aucune détection supplémentaire : $request->getLocale() suffit.

8 · Installation & déploiement

Environnement local

git clone git@github.com:PsycoSGWaK/portfolio.git
composer install
# Renseigner DATABASE_URL et APP_SECRET dans .env.local
php bin/console doctrine:database:create
php bin/console doctrine:migrations:migrate
symfony serve                # http://localhost:8000
PHP 8.4 obligatoire. Sur cette machine, Apache/WAMP tourne encore en PHP 8.3 : servir le projet par Apache en local échoue en erreur 500. Le serveur Symfony (symfony serve), lui, utilise le PHP 8.4 du PATH et fonctionne. Conséquence pratique : le .htaccess ne peut pas être testé localement, seulement sur le serveur.

Hébergement de production

Le site est hébergé chez o2switch, sur un mutualisé cPanel / CloudLinux. Le point important de la configuration est la séparation entre le dépôt et la racine web :

ÉlémentEmplacement
Dépôt complet~/repositories/guillaumehurard — invisible du web
Racine web~/public_html/guillaumehurard/public → lien symbolique vers ~/repositories/guillaumehurard/public
Secrets.env.local sur le serveur, permissions 600, non versionné
Logs applicatifsvar/log/prod.log
Pourquoi les logs ne vont pas sur stderr : la configuration Symfony par défaut envoie les logs de production vers php://stderr, qui n'atterrit nulle part de consultable sur ce compte — ni error_log, ni les journaux agrégés du cPanel, et /var/log/exim_mainlog est inaccessible (CageFS). monolog.yaml a donc été modifié pour écrire dans un vrai fichier, sans quoi tout diagnostic en production est impossible.

Déploiement continu

Tout push sur main déclenche le workflow .github/workflows/deploiement.yml. Le principe directeur : tout ce qui est coûteux ou fragile s'exécute sur le runner GitHub, jamais sur le mutualisé.

  1. Build sur le runner — composer install --no-dev puis asset-map:compile, avec PHP 8.4.
  2. Ouverture de l'accès SSH — l'IP du runner est ajoutée à la liste blanche du pare-feu via l'API cPanel SshWhitelist.
  3. Sauvegarde du .env.local de production.
  4. Mise à jour du code — git fetch + reset --hard origin/main côté serveur.
  5. Transfert des artefacts — rsync de vendor/, public/assets/ et assets/vendor/ uniquement.
  6. Migrations et reconstruction du cache.
  7. Health check — / et /en doivent renvoyer 200, sinon le job échoue.
  8. Fermeture de l'accès et effacement de la clé, exécutés quoi qu'il arrive.
Pourquoi cette répartition git / rsync ? Le code source arrive par git et seuls les artefacts non versionnés transitent par rsync. Cela évite tout --delete à la racine du projet — le .env.local ne peut donc pas être détruit par une erreur de configuration du transfert.
Deux contraintes de la liste blanche SSH. Le pare-feu d'o2switch filtre par IP source et n'accepte que 5 exceptions. Comme l'API ne permet pas de distinguer l'IP d'un runner de celle d'un poste de travail, le workflow commence par un remove_all. Conséquence directe : chaque déploiement supprime aussi l'IP personnelle, et l'accès SSH manuel doit être ré-autorisé depuis cPanel. Une suppression met environ cinq minutes à devenir effective.
Mécanisme précédent, conservé en secours : un script ~/deploy_guillaumehurard.sh déclenché par cron toutes les 10 minutes assurait le déploiement avant la mise en place du workflow. Sa ligne est commentée dans la crontab — les deux mécanismes ne peuvent pas cohabiter, le cron se réveillant potentiellement en plein rsync. Le script reste sur le serveur : décommenter la ligne suffit à revenir en arrière.
